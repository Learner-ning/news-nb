# 交付诚实性规范

> 制定时间：2026-09-17
> 适用范围：新闻树项目全部 Stage（Stage 0 起，含后续所有阶段）
> 规范性质：**约束性**（不是建议）。与各 Stage 执行规范并列，且**优先于**交付记录中任何自评结论。
> 触发原因：`docs/Stage-3.2.1-新闻树几何纠偏交付记录.md` 自评「超长放射线 0 条 / 节点重叠无」，与用户 21:14 实拍截图（中心扇形 + 十余根贯穿屏幕细线 + 外围卡片墙）**直接矛盾**。该记录写于代码提交之后、未经过浏览器实拍核验。

---

## 1. 定义

**交付诚实性**：指一份 Stage 交付记录中，「结论」与「可核验证据」之间必须存在一一对应的关系；凡未被证据支撑的结论，不得以「通过 / 已完成 / 已消除 / 无」等肯定性措辞出现。

三个基本概念：

```text
证据（Evidence）
  → 可被第三方独立复现的观测结果。例如：测试输出、几何计算脚本的原始输出、
    浏览器实拍截图、接口响应原文。

结论（Claim）
  → 交付记录中对某项要求是否达成的判定。例如：「超长放射线 0 条」「移动端无横向溢出」。

证据强度（Evidence Strength）
  → 证据对结论的支撑程度。分四级：
    L1 实拍    浏览器真实渲染截图（最强，可证伪视觉类结论）
    L2 实测    真实数据 + 真实运行链路的脚本输出（可证伪数值类结论）
    L3 代码    源码静态审查、正则审计、diff 关键字扫描（只能证伪「有没有写」，不能证伪「跑起来是什么样」）
    L4 推理    逻辑推导、几何复算、参数扫描（最弱，只能作为设计依据，不能作为验收依据）
```

**核心判定规则**：结论的证据强度必须 **≥ 该结论所属类别的门槛**（见 §4）。不达门槛的结论，必须降级措辞（见 §3 原则 4）。

## 2. 范围与边界

### 2.1 覆盖范围

| 对象 | 说明 |
|---|---|
| 全部 Stage 交付记录 | `docs/Stage-*.md`，含执行记录、验收记录、交付记录、评估报告 |
| 全部验收结论表 | 记录中出现的「通过 / 失败 / 已消除 / 无 / 0 条」等判定单元格 |
| 全部指标对比表 | 记录中出现的 before / after 数值对比 |
| 全部「禁止项」审计声明 | 「数据层一行未改」「未修改抓取」类声明 |
| 全部截图 / 对照页声明 | 记录中声称已提供的截图、对照页、原型页 |
| 提交信息（commit message） | 提交正文中对改动性质的描述 |
| 面向用户的最终回复 | 会话中对用户陈述的完成度、通过率、指标 |

### 2.2 不覆盖（明确边界）

| 不覆盖 | 原因 |
|---|---|
| 设计讨论、方案推演、取舍说明 | 属于设计过程，允许主观表述 |
| 「建议」「可以」「倾向」类措辞 | 非结论，不受本规范约束 |
| 已知限制的主动声明 | 主动声明限制本身就是诚实行为，无需额外证据门槛 |
| 第三方源站数据本身 | 源站抖动不可控；只约束「是否如实报告抖动」 |
| 未提交到仓库的临时探针脚本 | 探针本身无需入库，但其输出必须可被复现描述 |

### 2.3 与「不伪造数据」的区别

项目已有原则「不伪造数据」（不伪造发布时间、不登记不可达源为可用源）。**本规范约束的是第二层**：不伪造**结论**。二者关系：

```text
不伪造数据  → 数据层：条目、时间、来源、字段值
本规范      → 结论层：达成度、指标、通过与否、证据存在性
```

## 3. 原则

### 原则 1｜结论必须有证据，证据必须可复现

任何肯定性结论，必须在交付记录中同时给出：证据类型、证据来源（脚本路径 / 截图路径 / 命令）、原始数值。禁止只写结论不写证据。

### 原则 2｜区分「算出来的」与「看到的」

数值达标 ≠ 视觉达标。几何复算（L4）**不能**用于证伪视觉类要求。典型反例：Stage 3.2.1 计算出「超长放射线 0 条」，但实拍截图中放射线清晰可见——因为计算口径（枝脊长度）与视觉口径（枝脊 + 叶片簇外推后的整体放射感）不是同一件事。

### 原则 3｜未验证的一律标注「未验证」

凡因环境限制未能执行的验证（如沙箱无浏览器），必须在结论单元格内**显式**写「未验证（原因）」，不得写作「通过（代码级验证）」。代码级验证属于 L3，不能冒充 L1。

### 原则 4｜措辞强度必须匹配证据强度

| 证据等级 | 允许的措辞 | 禁止的措辞 |
|---|---|---|
| L1 实拍 | 「通过」「已消除」「无」 | — |
| L2 实测 | 「实测通过」「脚本验证为 0」 | 「视觉上已消除」「用户可见为无」 |
| L3 代码 | 「代码级确认存在」「静态审计 0 命中」 | 「通过」「已消除」 |
| L4 推理 | 「几何复算为 0」「理论推算」 | 「通过」「已消除」 |
| 无证据 | 「未验证」 | 任何肯定性结论 |

### 原则 5｜自评与证据分离呈现

交付记录中，「自评结论」与「证据」必须分列两栏。禁止把证据混入自评措辞中（如「已消除（实测 0 条）」应拆为两栏：结论「已消除」／证据「实测脚本输出 0 条」）。

### 原则 6｜发现不一致时以证据为准，并主动更正

当自评结论与证据（尤其用户实拍）冲突时：**以证据为准**，当轮修订记录，并在记录中保留「原结论 → 更正后结论 → 更正依据」三栏，不得静默覆盖。

### 原则 7｜禁止用「通过率」稀释未完成项

「50/50 通过」这类表述，必须同时说明测试覆盖的**是什么**。若测试只覆盖代码级断言、未覆盖视觉要求，必须写明「测试全通过，但 §20-A/§20-E/§20-F 视觉项未验证」。

## 4. 检查项与判定标准

### 4.1 证据门槛表（按结论类别）

| 结论类别 | 最低证据等级 | 具体形式 |
|---|---|---|
| 视觉类（第一眼是否像树 / 是否还有放射线 / 卡片是否在外围） | **L1 实拍** | `/` 与 `/source/:key` 的真实浏览器截图 |
| 交互类（拖动 / 缩放 / hover / 后退 / 刷新） | **L1 实拍** 或 **L2 实测** | 浏览器操作录屏、截图；或真实链路路由往返脚本输出 |
| 数值类（包围盒 / 缩放 / 字号 / 重叠数 / 载荷） | **L2 实测** | 真实数据驱动脚本的原始输出 |
| 边界类（移动端不横向溢出 / 断点） | **L1 实拍** | 375 / 768 / 1024 / 1440 四断点截图 |
| 禁止项审计（数据层未改 / 抓取未改） | **L3 代码** | `git diff` 关键字扫描 0 命中 + 文件清单 |
| 测试类（N/N 通过） | **L2 实测** | `node --test` 原始输出 |
| 结构类（路由存在 / 节点数） | **L3 代码** | 源码 + 单测断言 |

### 4.2 交付前必查清单

**证据存在性**

- [ ] 记录中每一条肯定性结论，都能在文中找到对应证据位置
- [ ] 所有截图声明指向**真实存在**的文件，且文件已入 `docs/`（不依赖本地临时路径）
- [ ] 所有数值均标注来源脚本或命令
- [ ] 环境受限项已显式标注「未验证」

**措辞一致性**

- [ ] 逐格核对：结论单元格的措辞是否 ≤ 其证据等级允许的上限（§3 原则 4）
- [ ] 无「通过（代码级）」「已消除（复算）」这类混合措辞
- [ ] 自评与证据分列呈现

**数值可复现性**

- [ ] before / after 数值均由**同一脚本、同一数据口径**产出
- [ ] 工作区存在未提交改动时，before 基线必须取自 `git show <base>:<file>` 而非工作区
- [ ] 换行符差异（CRLF/LF）已在比对前归一化

**禁止项审计**

- [ ] `git diff <base>..HEAD` 文件清单与记录声明一致
- [ ] 禁止项关键字审计命中数为 0，且**关键字列表已列出**
- [ ] 「未改」声明覆盖规范 §禁止修改 的每一项，逐项对应

**与用户实拍的一致性**

- [ ] 若用户提供了实拍截图，记录结论**必须**与截图一致
- [ ] 若不一致，已按 §3 原则 6 更正并保留三栏

### 4.3 判定标准（交付记录是否合格）

```text
合格
  → 全部肯定性结论均达到对应证据门槛
  → 全部未验证项已显式标注
  → 措辞强度全部匹配证据等级
  → 与用户实拍无矛盾

有条件合格
  → 存在未验证项，但已显式标注且说明原因与替代验证手段
  → 不影响该 Stage 的核心目标判定

不合格
  → 存在肯定性结论但无证据
  → 措辞强度超过证据等级（如 L4 写「通过」）
  → 与用户实拍矛盾且未更正
  → 截图声明指向不存在的文件
```

## 6. 违反后的处理方式

### 6.1 违规分级

| 级别 | 情形 | 处理 |
|---|---|---|
| **P0 虚假结论** | 无证据的肯定性结论；措辞强度超过证据等级；截图声明指向不存在文件 | 当轮修订记录；在记录顶部加「更正声明」；该 Stage **不计入完成**，需重新验收 |
| **P1 证据不足** | 有结论但证据为 L4 而门槛为 L1/L2；未标注未验证项 | 补证据或降级措辞；补做后可计入完成 |
| **P2 呈现问题** | 自评与证据未分列；关键数值缺来源标注 | 当轮修订格式即可，不影响完成判定 |

### 6.2 处理流程

```text
Step 1  定位
        → 逐条比对结论与证据，列出全部不达标项

Step 2  定性
        → 按 §6.1 分级（P0 / P1 / P2）

Step 3  更正
        → 在交付记录中保留「原结论 → 更正后结论 → 更正依据」三栏
        → 禁止静默覆盖原结论（保留可追溯性）

Step 4  补证
        → P0/P1 须补足证据；环境受限无法补证时，改为「未验证」并说明
        → 不得用新的 L3/L4 证据冒充 L1

Step 5  复验
        → 更正后重新按 §4.2 清单自查
        → P0 项须重新走该 Stage 的完整验收流程

Step 6  归档
        → 在当天工作日志中记录本次更正（含违反条款、更正内容）
```

### 6.3 对已交付 Stage 的追溯

本规范生效前已交付的记录（Stage 0 ~ 3.2.1），须做一次**回溯核查**：

| 检查对象 | 处理 |
|---|---|
| 结论表中有肯定性表述但无证据的单元格 | 降级为「未验证」或补充证据 |
| 声称有截图但文件不存在的 | 标注「截图缺失」，并在记录中说明 |
| 与用户实拍矛盾的 | 按 §3 原则 6 更正 |

**已知需回溯的记录**：`docs/Stage-3.2.1-新闻树几何纠偏交付记录.md` —— 「超长放射线 0 条」「节点重叠：无」两条与用户实拍矛盾，属 **P0**。

### 6.4 责任声明

交付记录由执行该 Stage 的一方撰写，**写入即视为对真实性负责**。不得以「自动化产出」「脚本结果」为由免除责任——脚本的口径选择本身即是人工决定。

## 7. 生效与例外

**生效**：本规范自 2026-09-17 起生效，适用于其后的全部 Stage。

**例外程序**：确有必要以低于门槛的证据支撑结论时，须在交付记录中单列「例外声明」，写明：例外条款、理由、替代验证手段、残余风险。未走例外程序的，一律按 §6 处理。

**例外上限**：视觉类（§4.1 第一行）结论**不适用例外程序**，必须 L1 实拍。
