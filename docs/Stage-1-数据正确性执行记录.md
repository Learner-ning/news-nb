## 2. 改动内容

### 2.1 Commit 1 —— HTML 清洗 / 正文截断 / 图片抽取

改动文件：`lib/news-core.mjs`（+37 / −12）

**① `stripHtml()` 执行顺序修正**（根因修复）

根因：部分源把 HTML 做了 entity 转义（IT之家 / 少数派 / GitHub热榜 / 雪球的 `<description>` 是 `&lt;p&gt;…`）。原实现「先删标签、后解码实体」，转义标签在删除阶段不可见、解码之后又原样「复活」，最终把 HTML 标签当正文输出。

```js
// 新顺序
解码 → 删 script/style → 删 CDATA 标记 → 删标签 → 再解码 → 再兜底删一次 → 空白归一化 → trim
```

**② 修复我在核对时发现的两个缺口**

| 缺口 | 现象 | 修复 |
|---|---|---|
| `extractImage()` 未先解码 | IT之家（entity 转义源）的 `<img>` 全部漏抽，只能抽到未转义源（爱范儿/触乐/华尔街见闻）的 34 张 | 改为先 `decodeEntities(raw)` 再匹配 → image 从 34 条提升到 **68 条** |
| CDATA 标记泄漏 | 雪球话题正文尾部出现裸露的 `]]>`（CDATA 标记被 entity 转义后解码露出） | 在清洗链中增加 `CDATA_MARK` 清理（两遍） |

**③ 正文截断移到清洗之后**

```js
const contentRaw = tag(body, "content:encoded") || tag(body, "description") || "";
const content = stripHtml(contentRaw);      // 先清洗成纯文本
const summary = content.slice(0, 240);      // 再截断，杜绝半截标签
```

**④ 图片抽取**

```js
export function extractImage(raw) {
  const s = decodeEntities(raw);
  const m = String(s || "").match(/<img\b[^>]*?\bsrc\s*=\s*["']([^"']+)["']/i);
  if (!m) return null;
  const url = decodeEntities(m[1]).trim();
  return /^https?:\/\//i.test(url) ? url : null;   // 相对路径 / data: 一律不采纳，无图保持 null
}
```

### 2.2 Commit 2 —— 热度算法归一化 + 叶片宽度统一

改动文件：`lib/news-core.mjs`、`public/js/tree-view.js`、`public/js/news-store.js`（+89 / −49）

**热度算法**：六项全部先归一化到 0~1 再加权；两个分支权重和严格 = 1；保留 `hasRealTime` 分支。

```js
const HEAT_WEIGHTS = {
  withTime: { fresh: 0.30, quality: 0.12, rank: 0.16, dup: 0.16, cat: 0.08, kw: 0.18 },  // = 1.00
  noTime:   { fresh: 0.12, quality: 0.12, rank: 0.34, dup: 0.16, cat: 0.08, kw: 0.18 }   // = 1.00
};
```

各项归一化方式：

| 项 | 归一化公式 | 取值分布 |
|---|---|---|
| fresh | `hasRealTime ? exp(-ageH/12) : 0.5` | 0~1（无真实时间固定 0.5） |
| quality | `clamp01((feedWeight - 0.8) / 0.4)` | 0.9→0.250、0.95→0.375、1.0→0.500、1.05→0.625、1.10→0.750、1.15→0.875 |
| rank | `clamp01(1 - (rank-1)/15)` | rank1→1.000、rank5→0.733、rank10→0.400、rank15→0.067、rank16+→0 |
| dup | `clamp01((dupCount-1)/3)` | 1源→0、2源→0.333、3源→0.667、4源→1.000 |
| cat | `clamp01(分类条目数 / 最大分类条目数)` | 0~1 |
| kw | `clamp01(命中数/3)` | 0、0.333、0.667、1 |

**叶片宽度**（`tree-view.js`）：

```js
const need = Math.min(textWidth(leafText(item.title)) + LEAF_PAD, LEAF_MAX_W);  // 340
const w = need * (LEAF_HEAT_LO + heat * (LEAF_HEAT_HI - LEAF_HEAT_LO));         // 0.95 ~ 1.15
this._leafW.set(item.id, Math.round(clamp(w, LEAF_MIN_W /*108*/, LEAF_MAX_W)));
```

- `leafText()`：截断前先剥掉残留 HTML 标签并归一化空白 → 保证永不出现半截标签
- `truncateByWidth()`：优先在中文标点/语义边界收尾（丢弃不足 20% 的尾巴），避免截出半截词
- `build()` 增加 `this._leafW.clear()`：宽度依赖 heatScore，刷新后必须重算
- 删除 `news-store.js` 的 `leafWidthFor` 死算法（连带清理 `textWidth` / `clamp` import）

**未触碰的部分**（逐项自检通过）：`layout()` 全部几何常量（`ROW_TOP/ROW_STEP/ROW_GAP/CLUSTER_GAP/CAT_GAP/X_MARGIN/PILL_H`）、`rowCap`（`cats.length<=1 ? 1020 : 560`）、无径向布局、无 LOD、无粒子。

### 3.2 每项变化原因

| 项 | 原因 |
|---|---|
| **fresh**（0.30 / 0.12） | 有真实发布时间时新鲜度仍是新闻最重要的信号，保持 0.30。无真实发布时间（热榜）时，时间信息本身缺失，只保留中性值 0.5 与一半权重（0.12），把 0.18 让给 `rank` —— 否则热榜条目会靠"未知新鲜度"白拿 0.30 权重。 |
| **quality**（0.28 → 0.12） | 旧实现 `quality = min(1, 0.55 + w×0.42)`，当 `w ∈ [0.9, 1.15]` 时 quality ∈ [0.928, 1.0]，**0.28 的权重只产生 0.072 × 0.28 ≈ 0.02 的实际分差**，等于白占 28% 权重。新实现把源权重线性展开到 0~1（区分度 **0.625**），因此不需要大权重：0.12 即可产生 **≈0.075** 的实际分差，比旧实现更大。 |
| **rank**（0.14 → 0.16 / 0.34） | 旧 `rankBonus` 上限仅 0.16，再乘 0.14 → **区分度只有 0.043**（rank1 与 rank15 几乎同分）。归一化到 0~1 后 0.16 权重即可产生 0.16 分差；noTime 分支再吸收 fresh 让出的 0.18 达到 **0.34**，使热榜条目仍按名次强烈区分（实测 rank1 vs rank15 差 **0.317**）。 |
| **dup**（0.18 → 0.16） | 旧 `dup = min(0.3, (dupCount-1)×0.15)` 上限 0.3，乘 0.18 后最大贡献仅 0.054，且实测**恒为 0**。归一化 0~1 后 0.16 权重可产生完整 0.16 分差（实测 dupCount 1→4 差 **0.160**）。权重略降是因为归一化后单位效率提高。 |
| **cat**（0.08 不变） | 旧 `catFreq ≤ 0.06`，乘 0.08 → **贡献上限 0.0048**，形同虚设。归一化到 0~1 后 0.08 权重可产生 0.08 分差（实测最大/最小分类差 **0.064**）。权重无需调整，问题在归一化而非权重。 |
| **kw**（0.12 → 0.18） | 旧实现 4 个关键词即封顶在 0.12（单关键词 0.035）。归一化为「命中 3 个即满分」后，0.18 权重可产生完整 0.18 分差。关键词表是人工维护的强信号，适当提高权重合理。 |

## 5. 未达标项：heatScore 不同值数量（52% < 70%）

### 5.1 实测结果

| 分组 | 条目数 | 不同 heatScore 值 | 唯一率 |
|---|---|---|---|
| 新闻（有真实发布时间） | 110 | 87 | **79%** ✅ |
| 热榜（无真实发布时间） | 100 | 36 | **36%** ❌ |
| 新闻（无真实发布时间） | 14 | 1 | **7%** ❌ |
| **合计** | **224** | **117** | **52%** ❌（要求 ≥157） |

并列结构：**43 个并列组**，涉及 148 条；最大一组 **14 条**。

### 5.2 根因（输入相同 → 分数必然相同）

| 并列组 | 规模 | 原因 |
|---|---|---|
| `0.168` | 14 条 | **全部来自 GitHub热榜**（唯一无 pubDate 的 RSS 源），同源、同分类、无关键词命中、无互动量、无多源合并 → 六个输入项完全一致 |
| `0.397` / `0.297` | 各 6 条 | 热榜同 rank、同源权重档位、无关键词 |
| 各 rank 组 | 每 rank 7 条 → 仅 3 个不同值 | 7 个热榜平台中 **5 个权重相同（0.9）**、2 个为 0.95；同一名次在不同平台的可区分输入只剩 `feedWeight`(2 档) × `kw`(4 档)，实际多为 0 关键词 |

即：**热榜条目的可区分维度天然只有「名次 × 平台权重 × 关键词」**，而平台权重只有 2 档、关键词大多未命中，所以 100 条热榜只能产生 36 个不同值。

### 5.3 三个可选方案（需要你裁决）

| 方案 | 做法 | 预估效果 | 代价 / 风险 |
|---|---|---|---|
| **A. 差异化平台权重** | 把 `HOT_SOURCES` 里 7 个平台的 `weight` 改成互不相同（如 0.88/0.90/0.92/0.94/0.96/0.98/1.00） | 热榜不同值 36 → 约 100，合计约 **86%** ✅ 达标 | **属于"修改新闻源配置"**，Stage 1 明确禁止；且权重是主观参数，需要你认可排序意图 |
| **B. 加入互动量维度** | 用已有的真实字段 `praise`（澎湃）/ `discuss`（贴吧）/ `hotTag`（微博）做第 7 个归一化项 | 离线模拟仅能到约 **60%**，仍不达标 | 仅 40/100 热榜条目有该数据 → 对无此字段的平台系统性不公平 |
| **C. 接受并列（现状）** | 不改 | 52%，不达标 | 并列真实反映"输入相同"，属于诚实结果；但排序信息量在热榜侧偏低 |

**我的建议**：选 **C（Stage 1 内接受并列）+ 把 A 放到 Stage 5**（"分类与源生态"阶段本来就要重新校准各源权重与补齐源，那时一起做更合适）。理由：

1. 在 Stage 1 强行达标，只能靠"差异化平台权重"或"给分数加人为噪声"——后者违反本项目最重要的纪律（**不伪造数据**）；
2. 本 Stage 的核心问题（权重和 >1、quality 无区分度、dup 恒为 0、catFreq 形同虚设）**已经真正解决**，六项全部归一化且区分度实测大幅提升（见 §4.4）；
3. 若你希望 Stage 1 就达标，**请批准方案 A**，我可以在 10 分钟内完成并复测（只改 `HOT_SOURCES` 的 weight 数值，不动源数量、不动分类）。

### 5.4 关于验收标准的说明

"不同值数量 ≥ 条目数 × 70%" 度量的是**分数分辨率**，而并列本身由**输入数据是否相同**决定，不完全由算法决定。本次已做到：能区分的都区分了（新闻侧 79%），无法区分的（同源同类无关键词的 14 条 GitHub 热榜条目）在数学上不可能区分——除非引入新信息或人为噪声。
